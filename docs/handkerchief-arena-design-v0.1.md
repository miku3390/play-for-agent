# 丢手绢 · AI 对战平台 —— 设计架构与项目框架

**v0.1** · 2026-10-06 · 状态：待拍板

---

## 0. 摘要

三句话。

**一、原版规则有一个会把游戏玩死的洞。** 攻方"整轮不丢手绢"永远不比"丢下"更差，这是弱占优策略。双方按各自最优策略行动，整局比赛不会出现一次丢手绢动作。

**二、修法不是调数值，是给时间装双向计价。** 等待成本只压在守方身上，攻方等待免费，博弈论给出的答案必然是"不动"。改成双方每等一回合各付 1 点，博弈立刻活过来：策略熵从 0 bit 升到 2.88 / 2.76 bit。

**三、平台的第一版不是平台。** 是引擎库 + CLI 对战 + 回放。Web、账号、天梯排到 M3 之后。M0 先写模拟器把参数扫完再定稿——这份文档里的每一张表都来自扫描器。

## 1. 规则诊断

### 1.1 把原版规则写成矩阵

按 KIMI 那版口径：守方检查时手绢已丢 → 守方 +5、攻方 −10；手绢未丢 → 守方 −10、攻方 0；等待成本只在守方检查时结算；第 10 回合强制检查。

枚举攻方 11 个策略（第 1~10 回合丢，或整轮不丢）× 守方 10 个策略（第 1~10 回合检查）：

| 攻方策略 | 最差收益 | 最好收益 |
| --- | ---: | ---: |
| 第 1 回合丢下 | −10 | −10 |
| 第 2~10 回合丢下 | −10 | 0 |
| 整轮不丢下 | **0** | **0** |

"整轮不丢下"的收益恒为 0，从不低于 0；其余每一个策略的最差收益都是 −10。

这是弱占优策略。理性代理只要发现它，就不会再考虑丢手绢。

### 1.2 均衡长什么样

虚构博弈（fictitious play）迭代 6 万轮的收敛结果：

| | 收敛策略 |
| --- | --- |
| 攻方 | 整轮不丢 **100%** |
| 守方 | 第 1 回合检查 **100%** |
| 单轮收益 | 攻方 0 / 守方 −10 |

守方每轮固定掉 10 点血，50 点血撑 5 轮。胜负与策略无关，只与谁先当守方有关。**"丢手绢"这个动作在整局中一次都不会发生。**

### 1.3 补一刀也救不回来

给"整轮不丢"加一条 −15 的失职罚：

| | 收敛策略 |
| --- | --- |
| 攻方 | 第 9 回合丢 50% / 第 10 回合丢 50% |
| 守方 | 第 10 回合检查 100% |
| 单轮收益 | 攻方 −10 / 守方 −4 |

前 9 个回合双方都在等。10 回合这个数字在这里只剩下装饰作用。

顺带一提，这条数据说明：**给"不行动"加罚只能把退化往后推一格，推不掉。**

### 1.4 根因

把"等待"按角色拆开看：

| 角色 | 每多等一回合付出的代价 |
| --- | --- |
| 攻方 | 0 |
| 守方 | 1（等待成本的增量） |

时间对攻方免费，对守方收费。

攻方的推理链很短：等下去不花钱，那为什么要动？守方的推理链同样短：攻方随时可能丢，早查等于送 10 点，那就等到底。两个"最优"合起来，把前 9 个回合抹掉了。

### 1.5 修法：双向时钟

> 每经过一回合，双方各累积 1 点疲惫值，在各自结算时从 HP 扣除。

攻方的计息在"丢下"那一刻停止，守方的计息在"检查"那一刻停止。

扫描 3×3 的时钟强度组合（每格 = 攻方时钟 / 守方时钟）：

| 攻/守时钟 | 攻方策略熵 | 守方策略熵 | 收益（攻/守） | 整局轮数 | 先手胜率 | 双亡率 | |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 0 / 0 | 1.00 | 0.00 | −10.0 / +5.0 | 17.0 | 100% | 0% | 退化 |
| 0 / 1 | 0.00 | 0.01 | −10.0 / −4.0 | 7.0 | 100% | 0% | 退化 |
| 0 / 2 | 2.81 | 0.00 | 0.0 / −10.0 | 9.0 | 0% | 0% | 退化 |
| 1 / 0 | 0.01 | 0.00 | −10.0 / +5.0 | 17.0 | 100% | 0% | 退化 |
| **1 / 1** | **2.88** | **2.77** | **−10.1 / −4.0** | **6.4** | **51%** | **7%** | **健康** |
| 1 / 2 | 2.81 | 0.00 | 0.0 / −10.0 | 9.0 | 0% | 0% | 退化 |
| 2 / 0 | 0.00 | 2.00 | −10.0 / +5.0 | 17.0 | 100% | 0% | 退化 |
| **2 / 1** | **2.84** | **2.94** | **−10.4 / −4.1** | **6.1** | **53%** | **6%** | **健康** |
| 2 / 2 | 2.81 | 0.00 | 0.0 / −10.0 | 9.0 | 0% | 0% | 退化 |

熵是策略分布的香农熵（bit）。上界是 log₂11 ≈ 3.46（攻方）和 log₂10 ≈ 3.32（守方），熵接近 0 就是退化成纯策略。

九个格子里只有两个活。**单向时钟（任何一边是 0）一律死**，双倍时钟（2/2）也死——守方等不起，第 1 回合就查，攻方从此不丢。

推荐 **1 / 1**：对称、好解释、参数最少。2 / 1 备选，用于给攻方加压。

### 1.6 第二条硬约束：失职罚必须严格大于命中惩罚

固定时钟 1/1，扫失职罚：

| 失职罚 | 攻方策略熵 | 守方策略熵 | "整轮不丢"占比 |
| ---: | ---: | ---: | ---: |
| 0 | 0.01 | 0.01 | 100% |
| 5 | 0.01 | 0.01 | 100% |
| 8 | 0.01 | 0.01 | 100% |
| 10 | 1.07 | 0.10 | 50% |
| 12 | 2.88 | 2.77 | 0% |
| 15 | 2.88 | 2.77 | 0% |
| 30 | 2.88 | 2.77 | 0% |

阈值卡在 10 到 12 之间，正好是命中惩罚（−10）的位置。

**设计定律：什么都不做的代价，必须高于做了但被抓的代价。** 否则理性代理选择什么都不做。

这条可以直接推广到以后加的任何机制上：只要某个动作的期望损失低于"不动"，它就会被绕过。

### 1.7 关于其余参数

| 参数 | 扫描结果 |
| --- | --- |
| 命中奖励 5 → 10 | 熵掉到 2.41，先手优势升到 57%，平衡变差。保持 5。 |
| 查空时额外罚攻方 0 → 5 | 健康，守方熵升到 2.94，但先手优势同时涨到 54%。可选，不划算。 |
| 查空时额外罚攻方 8 | 双亡率冲到 15%，越界。 |
| 查空时额外罚攻方 10 | 完全退化，先手 100%。别碰。 |
| 命中时也扣等待成本（"检查前经过的回合数"按字面一律扣） | 在命中奖励 5 下直接退化；要配命中奖励 10 才能活。**不推荐**——改动大，收益小。 |

## 2. 规则 v1.0（基准）

### 2.1 术语

原始描述里"轮"和"回合"混用过。统一如下：

| 术语 | 定义 |
| --- | --- |
| **回合**（turn） | 最小决策单位，双方同时秘密出牌 |
| **轮**（round） | 一次完整的攻守对峙，终结于守方检查或走满 10 回合 |
| **局**（match） | 从开局到一方 HP ≤ 0 的完整比赛 |

### 2.2 一局的骨架

1. 双方各 50 HP，裁决先手（随机或约定）。
2. 进入一轮：
   - 手绢状态置为"未丢"，回合号 t = 1
   - 逐回合推进，双方同时出牌
   - 守方某回合出 CHECK，或 t 走到 10 → 本轮结束并立即结算
   - 结算后攻守互换，回到第 2 步
3. 任一方 HP ≤ 0 → 该方判负。

### 2.3 动作

| 角色 | 动作 | 含义 |
| --- | --- | --- |
| 攻方 | DROP | 本回合丢下手绢，状态变"已丢"，不可撤销 |
| 攻方 | HOLD | 本回合不丢 |
| 守方 | CHECK | 本回合检查，本轮立即结束 |
| 守方 | WAIT | 本回合不检查 |

双方动作同时提交。攻方的动作对手不可见，手绢状态对手不可见。

### 2.4 结算表

记攻方丢下的回合号为 d，守方检查的回合号为 t。

| 情况 | 触发条件 | 守方 HP | 攻方 HP |
| --- | --- | ---: | ---: |
| **命中** | 手绢已丢（含本回合同时丢、含 t = 10 强制检查） | +5 − (t−1) | −10 − (d−1) |
| **误判** | 守方第 t 回合检查，手绢尚未丢 | −10 − (t−1) | −(t−1) |
| **失职** | t = 10，手绢整轮未丢 | −10 − 9 | −9 − 15 |

其中 (t−1) 是守方的疲惫值，(d−1) 是攻方的疲惫值——**攻方的计息在丢下那一刻停止，守方的计息在检查那一刻停止。**

三条分支合起来就是全部。没有第四种情况。

### 2.5 参数表

| 参数 | 符号 | 基准值 | 可调范围 | 备注 |
| --- | --- | ---: | --- | --- |
| 初始血量 | HP₀ | 50 | 30 ~ 80 | 只影响局长度 |
| 单轮回合上限 | T | 10 | 8 ~ 12 | 影响对峙长度 |
| 双方时钟 | chrono | 1 | 只能整档调 | **改 0 或 2 都会退化** |
| 命中奖励（守） | — | +5 | 5 ~ 7 | 提到 10 会破坏平衡 |
| 命中惩罚（攻） | — | −10 | −10 ~ −15 | |
| 误判罚（守） | — | −10 | −8 ~ −12 | |
| 误判罚（攻） | — | 0 | 0 ~ 5 | 超过 8 会退化 |
| 失职罚（攻） | — | −15 | **必须 > 10** | 见 1.6 |

基准配置的均衡形态（供 M2 校验用）：

```
攻方： d1 39.5%  d2 6.0%  d3 7.7%  d4 6.2%  d5 6.5%
        d6 7.0%  d7 4.8%  d8 8.1%  d9 6.6%  d10 7.8%  永不丢 0%
守方： k1 8.5%  k2 9.0%  k3 7.6%  k4 6.7%  k5 6.3%
        k6 5.5%  k7 4.9%  k8 4.8%  k9 3.7%  k10 43.1%
单轮收益：攻方 −10.02 / 守方 −4.08
策略熵：2.88 / 2.76 bit（上界 3.46 / 3.32）
整局：6.4 轮（≈ 32 回合），先手 52% / 后手 40% / 双亡 8%
```

两个"反直觉"的点，值得记住：

- **攻方 40% 会在第 1 回合就丢。** 不是莽，是因为守方 43% 会拖到第 10 回合，而攻方的计息在丢下那一刻就停了——早丢是止损。
- **守方 43% 拖到第 10 回合。** 因为攻方 40% 在第 1 回合就丢，早查等于把 +5 换成 −10。

剩下 9 个回合分摊了余下的概率。这就是"欺骗与反欺骗"活着的样子。

### 2.6 健康度指标（M0 验收用）

一份参数配置合不合格，看这五条：

| 指标 | 阈值 |
| --- | --- |
| 双方策略熵 | ≥ 2.0 bit |
| 先手胜率 | 45% ~ 55% |
| 双亡率 | ≤ 10% |
| "整轮不丢"占比 | ≤ 5% |
| 单轮收益差 | 任一方不得为正且绝对值 > 5 |

## 3. 平台架构

### 3.1 分层

```
┌───────────────┐   ┌────────────────┐
│  观战 / 回放   │   │  排行榜 / 天梯  │
└───────┬───────┘   └───────┬────────┘
        └────────┬──────────┘
        ┌────────┴────────┐
        │  编排 Runner     │  超时 / 重试 / 判定 / 日志
        └───┬─────────┬───┘
    ┌───────┴──┐  ┌───┴────────┐
    │ 规则引擎  │  │ 代理适配层  │  code / llm / remote
    │ 纯状态机  │  └───┬────────┘
    └───────┬──┘      │
        ┌───┴─────────┴───┐
        │  状态投影 + 隔离  │
        └─────────────────┘
```

引擎是纯函数：**（状态，动作对）→ 新状态 + 事件列表**。不含 IO、不含时钟、不含随机（随机源由调用方注入）。这样它可测、可回放、可重放。

### 3.2 信息隔离

这是整个平台最容易做错、也最容易毁掉比赛公平性的地方。三条铁律：

**一、引擎内部状态不离开引擎进程。** 攻守双方各自有一个 Projection 函数，输出里**不存在** handkerchief_dropped 这个 key——不是置 null，不是写 "unknown"，是整个字段不出现。字段不存在和字段为 null，对 LLM 代理来说是完全不同的心理暗示，"unknown" 这个词本身就在提示"这里有事"。

**二、代理不接触全量状态。** 代码代理跑在子进程，只通过 stdin/stdout 交换"动作请求 / 动作响应"；LLM 代理的提示词由同一个 Projection 渲染。禁止把整个 state 序列化后塞进 prompt——这条要在 code review 里当红线守。

**三、日志双版本。** 裁判日志（全量，用于回放和审计）和选手日志（各自的投影，用于 debug）。CI 里跑投影测试：拿裁判日志重放一遍 Projection，断言输出中不含任何敏感字段名。

### 3.3 代理接入

统一抽象：输入一个 observation，输出一个 action。三种形态共用同一份 schema。

| 形态 | 载体 | 用途 |
| --- | --- | --- |
| A · 进程内 | Python / TS 函数 | 基准代理、单元测试 |
| B · 子进程 | JSONL over stdio | 用户提交的代码，沙箱隔离 |
| C · 远程 | HTTP / WebSocket | 跨语言、在线对战、LLM 代理 |

LLM 代理是形态 C 的特例，由平台的模型网关代跑，参赛者提交的是提示词与模型标识。

### 3.4 数据模型

```jsonc
// 一回合的观察（守方版本）
{
  "match_id": "...",
  "round": 3,
  "turn": 4,
  "role": "defender",
  "my_hp": 42, "opp_hp": 38,
  "my_history": [ {"turn":1,"action":"WAIT"}, ... ],
  "rounds_played": 2
  // 注意：没有 opp_history，没有 handkerchief，什么都没有
}

// 一回合的观察（攻方版本）
{
  "match_id": "...", "round": 3, "turn": 4, "role": "attacker",
  "my_hp": 38, "opp_hp": 42,
  "handkerchief_dropped": false,   // 只有攻方能看到
  "drop_turn": null,
  "my_history": [...], "rounds_played": 2
}

// 回放记录（每轮一条）
{ "round": 3, "turns": [ {"t":1,"atk":"HOLD","def":"WAIT"}, ... ],
  "outcome": "HIT", "d": 4, "t": 4, "hp_delta": {"attacker": -13, "defender": 2} }
```

### 3.5 沙箱、超时与成本

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 单回合决策超时 | 2 秒 | 超时动作 = 攻方 HOLD / 守方 WAIT |
| 连续超时 | 3 次判负 | 防"故意超时拖延" |
| 代码沙箱 | 子进程 + 资源上限 | 起步不上容器；上云再考虑 |
| LLM 单局预算 | 可配置 token 上限 | 超预算自动降级为兜底策略 |
| 网络 | 代码代理禁止出网 | 远程代理走形态 C 的专用通道 |

## 4. 项目框架

### 4.1 目录结构

```
handkerchief-arena/
├─ engine/          规则引擎（纯函数，无 IO）
│   ├─ state.py         状态定义与不变量
│   ├─ rules.py         结算规则（2.4 那张表）
│   └─ projection.py    双方视图 + 信息隔离
├─ runner/          对局编排：调度、超时、日志、终局判定
├─ agents/          代理适配层
│   ├─ base.py          统一接口
│   ├─ baselines/       随机 / 贪心 / 欺骗 / 耐心 四个基准
│   └─ llm.py           模型网关适配
├─ lab/             离线实验
│   ├─ balance_scan.py  平衡扫描器（附录 B）
│   └─ tournament.py    循环赛 / ELO
├─ gateway/         HTTP + WebSocket 服务（M3）
├─ web/             观战前端（M3）
├─ tests/
└─ docs/
```

### 4.2 里程碑

| 阶段 | 交付物 | 出口标准 |
| --- | --- | --- |
| **M0** 模拟器 | balance_scan.py | 能复现本文档全部表格；一次全参数扫描 < 60 秒；输出健康度五指标 |
| **M1** 引擎 + CLI | engine/ + runner/ | 两个代理从命令行打完整局并输出 JSONL 回放；单测覆盖结算表的每条分支；投影测试通过 |
| **M2** 基准代理 + 定参 | agents/baselines/ | 四类基准代理跑通循环赛；用实测数据敲定 v1.0 参数；ELO 能区分强弱 |
| **M3** 本地服务 + 观战 | gateway/ + web/ | WebSocket 推流；浏览器里能看完一整局并回放时间轴 |
| **M4** 平台化 | 账号 / 提交 / 天梯 / 沙箱 | 外部用户能提交 LLM 提示词并参赛；单局成本可核算 |

M0 到 M2 之间不打前端。规则没定稿就开始画界面，等于把返工写进计划。

### 4.3 风险

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| 平衡退化 | 策略熵 < 1.5 bit，或某策略占比 > 90% | 重跑扫描；检查失职罚是否 > 命中惩罚、时钟是否为 1 |
| 信息泄漏 | 代理在"不该知道"的时刻做出正确反应 | CI 投影测试；裁判日志与选手日志分离 |
| LLM 成本失控 | 单局 token 超预算 | 熔断 + 兜底策略；提示词做缓存 |
| 提前平台化 | M0-M2 未验收就启动 M3 | 里程碑门禁，不通过不启动 |
| 数值手调 | 靠直觉改参数 | 任何参数改动必须附一份扫描结果 |

## 附录 B · 复现

本文档所有表格由 tools/balance_scan.py 生成，纯标准库，Python 3.10+：
